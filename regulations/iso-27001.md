# ISO/IEC 27001, Information Security Management Systems, Requirements (ISO 27001)

- Scope id: `iso-27001` (standard)
- Jurisdiction: International (ISO/IEC)
- Version: ISO/IEC 27001:2022 (2022-10-25)
- Official text: https://www.iso.org/standard/27001
- Requirements: 74 (7 implemented, 3 configurable, 45 facilitated, 19 out-of-scope)
- Browse: https://pryv.github.io/compliance-matrix/#/scope/iso-27001

## ISO 27001 4: Clause 4 Context of the organization

Coverage: out-of-scope · draft

Requirement: Organization shall determine external and internal issues relevant
to its purpose that affect its ability to achieve the intended
outcomes of the ISMS, and shall determine interested parties +
requirements + scope.

**What Pryv does for you**

Clause 4 is the organization's strategic ISMS-scoping exercise.
Pryv has no software role at this layer, when an organization
adopts Pryv, the matrix supports their Clause-6 risk assessment
by enumerating Pryv-side controls explicitly, but Clause 4 itself
sits at the operator/implementer level.

## ISO 27001 A.5.15: A.5.15 Access control

Coverage: implemented · effort saved: high · draft

Requirement: Rules to control physical and logical access to information and
other associated assets shall be established and implemented based
on business and information security requirements.

**What Pryv does for you**

Logical access control is enforced at the API surface by the
access + permissions primitives; every read/write request is
checked against the access's stream + level permissions. The
operator's access-control rule definition (who gets what) is
the policy half; technical enforcement is Pryv-side.

**Detail**

**OAuth2 redirect + scope enforcement.** Pryv's delegated-app
authorization path (OAuth2 authorization-code + PKCE,
`open-pryv.io/components/oauth2/`, open-pryv.io 2.0.0-rc.8)
enforces access rules at two points: presented redirect URIs are
validated by exact string match (single loopback-port carve-out
per RFC 8252 / 9700; fragment-bearing URIs rejected,
`open-pryv.io/components/oauth2/src/clientRegistry.ts`), and the
minted app access carries only the user's granted subset of the
referenced consent offer's permissions. PKCE (S256) is mandatory
for every client.

**OAuth2 access rules added in open-pryv.io 2.0.0-rc.64 to
2.0.0-rc.77.** A consent for an operator-registered client never
grants account or system streams, `*` or `manage`, and by default
forbids creating accesses or webhooks and sharing secrets; the
grant's reach follows withdrawal and narrowing at once, the
accesses the app's sessions created included `[OE31]`, `[OSUB3]`,
`[OACR1]`. An aliased session is accepted under its alias only
`[AL13]`. An authorization for an account address is bound to the
signed-in account `[OPUE2]`. Token exchange gives a resource server
a token no wider than the one it replaces, only for a token issued
for one of its audiences `[OTX05]`; the replaced token is refused
at the API by default since open-pryv.io 2.0.0-rc.82
(`oauth.audienceBoundSessions: true`; an operator may set `false`)
`[OTXE02]`. Detail on
`hipaa-security.164.312(a)(1)`.

**Delegate-account token class.** Account delegation
(`open-pryv.io/components/delegation/`) adds an owner-equivalent
delegate token one account holds over another. It is bound by the
same per-stream permissions as any token; its access-control
property is the non-forgeable, authoritative teardown, a delegate
can never remove a delegation, and dissolving one requires a
genuine login on the controlled account (a personal token with no
forge-protected delegation marker). The `:_delegation:*`
namespace is plugin-owned and guarded end to end (no user
create/write/delete; internal subtree read-guarded and excluded
from wildcard reads); each delegate's actions are audited on the
controlled account. See `context/delegation-model.md`.

**Plugin-managed and account streams, by every spelling of an id**
(open-pryv.io 2.0.0-rc.56). The guards of the delegation
namespace, of the plugin-managed regions of the cross-account
(CMC) namespace (`:_cmc:`, its inbox and internal streams;
`:_cmc:apps` stays open to apps) and of the account fields judge
the stream an id resolves to, whatever store-prefixed spelling a
request uses, for every token, the owner's included; they also
refuse creating a stream under, or moving one into, a
plugin-managed parent `[CNRP1]`, `[CNRP6]`, `[CNRP7]`, `[DSC05]`.
On access creation and update a permission naming an account
field through such a spelling is judged, and stored, as that
field, so an app holding only a `*` grant on the regular streams
cannot hand one out `[ASA3]`, `[ASA6]`. Before this release a
store-prefixed spelling (`:local:<id>`, or the account store's
prefix) was not recognised by these guards, so the rule above
held only for requests using the canonical ids.

**Moving a stream** (open-pryv.io 2.0.0-rc.56). A move (a new
`parentId`) by an app or shared access needs manage rights on
every stream of the moved subtree, trashed ones included, as
deleting it does `[SMV1]`, `[SMV4]`; a parent inside the moved
subtree is refused for every access `[SMV10]`. Before it, a child
granted to the moving access at a lower level travelled into the
target parent's inherited permissions.

Apps a delegate authorizes on the controlled account get a scoped
`app` access, never the owner-equivalent token; the server marks
it as granted through the delegation (no client can forge the
mark) and removes it with the delegation `[DCH01]`, `[DCH03]`,
`[DCH12]`. In open-pryv.io 2.0.0-rc.23. Since open-pryv.io
2.0.0-rc.30 the rule also covers cross-account (CMC) data grants:
a delegate may accept one for the controlled account, the grant
carries the same mark (reported by `access-info`) `[DCH15]`, the
accept event names the approving delegate, server-stamped
`[DCH16]`, and the detach deletes the grant and notifies the
requester `[DCH18]`. Since open-pryv.io 2.0.0-rc.31 the account
holder, detaching the delegate, may keep named CMC data grants
that delegate gave (`keepAccessIds`): a kept grant loses the mark
and becomes the holder's own `[DCH21]`, a list naming any other
access is refused whole before any change `[DCH23]`, and every
other access granted through the delegation is removed as before.
Grant paths that still cannot record the
mark (OAuth2 consent, publishing a CMC offer, widening a CMC
grant) refuse delegation-derived tokens `[DCH17]`, `[OE27]`.

**Member accesses of a group account** (open-pryv.io 2.0.0-rc.53,
release commit `61fb28dd`,
https://github.com/pryv/open-pryv.io/issues/158). For a team
sharing one account, the rule Pryv enforces is: a member obtains
an access on a patient account only through a membership the
group's administrator approved, only for patient relationships
under the member's team streams, only for named data streams
within the patient's offer (the patient's core re-checks them
against the grant and stamps the member on the access), and only
for a bounded time (24 h by default, 60 s to 7 d,
`cmc.memberAccess.*`, never beyond the membership's expiry)
`[GA12]`, `[GA14]`, `[GA15]`, `[MB10]`, `[CMCMA]`; the access
cannot manage accesses and is deleted when the membership ends
`[GA20]` or the patient withdraws `[GA24]`. See
`context/workforce-access-patterns.md`, Pattern 3.

**Evidence**

- tests: AA01, AA02, ACCP, DCH01, DCH03, DCH12, DCH15, DCH16, DCH17, DCH18, DCH21, DCH23, OE27, CMCGA, CMCMA, GA12, GA14, GA15, GA20, GA24, MB10, CNRP1, CNRP6, CNRP7, DSC05, ASA3, ASA6, SMV1, SMV4, SMV10, OE31, OSUB3, OACR1, AL13, OPUE2, OTX05, OTXE02
- config keys: cmc.memberAccess.defaultTtl, cmc.memberAccess.minTtl, cmc.memberAccess.maxTtl, oauth.audienceBoundSessions

## ISO 27001 A.8.2: A.8.2 Privileged access rights

Coverage: configurable · effort saved: medium · draft

Requirement: Allocation and use of privileged access rights shall be restricted
and managed.

**What Pryv does for you**

Pryv's privileged-access surface is small and explicit: the
operator's `auth.adminAccessKey` is the root credential; system
streams (account, password, mfa) require an explicit grant in
`permissions[]`. Both surfaces are auditable. The operator's
custody process for the admin key is the policy-side control.

**Detail**

The account-field guards (the primary email, written only through
`account.update`; the non-editable and hidden fields; the level
caps on account-stream permissions) judge the canonical stream id
whatever store-prefixed spelling a request uses, on
`events.create` / `update` / `delete` and on `accesses.create` /
`update`, since open-pryv.io 2.0.0-rc.56 `[ASA1]`, `[ASA2]`,
`[ASA3]`, `[ASA6]`. Before that release a store-prefixed spelling
of an account field was not recognised by these guards: an access
holding `contribute` on the email field could change the primary
email (the password-reset address) through the events API, and an
app holding only a `*` grant on the regular streams could grant
an account field to an access it created. Upgrading is the fix;
no setting closes it on earlier releases.

**Evidence**

- tests: LG20, GF33, ASA1, ASA2, ASA3, ASA6
- config keys: auth.adminAccessKey
- primitives: access, system-streams

## ISO 27001 A.8.3: A.8.3 Information access restriction

Coverage: implemented · effort saved: high · draft

Requirement: Access to information and other associated assets shall be
restricted in accordance with the established topic-specific
policy on access control.

**What Pryv does for you**

Per-stream permissions are the technical access-restriction
primitive. Stream design (which data lives where) is the
implementer's choice; permission scoping per access is
operationally enforced at every API call.

**Detail**

A permission on a stream reaches its descendants, so moving a
stream changes who reaches its subtree. Since open-pryv.io
2.0.0-rc.56 an app or shared access may move a stream (a new
`parentId`) only with manage rights on every stream of the moved
subtree, trashed ones included, in addition to manage on the
target parent; otherwise `403 forbidden` and nothing moves
`[SMV1]` to `[SMV5]`. A parent inside the moved subtree is refused
for every access `[SMV10]`. Before that release a child granted
to the moving access at a lower level (`read`, `create-only`,
`none`) moved along and took on the permissions other accesses
held on the target parent. Renames and updates that keep the
current `parentId` are unchanged.

**Evidence**

- tests: AA01, AA02, ACCP, SMV1, SMV2, SMV3, SMV4, SMV5, SMV10
- primitives: access, permissions, stream

## ISO 27001 A.8.5: A.8.5 Secure authentication

Coverage: implemented · effort saved: high · draft

Requirement: Secure authentication technologies and procedures shall be
implemented based on information access restrictions and the
topic-specific policy on access control.

**What Pryv does for you**

Token-based auth by default; multi-factor via `mfa.*` API methods,
live by default since open-pryv.io 2.0.0-rc.14 (`services.mfa.active`;
TOTP built in, SMS providers pluggable) `[MA15A]`, `[MA15C]`. The MFA
acceptance series (`[MFAA]`) exercises activate `[MA3A]`,
`[MA10A]`, confirm `[MA4A]`, challenge `[MA5B]`, verify `[MA5A]`,
`[MA11A]`, deactivate `[MA6A]` and recover `[MA7A]`. Authentication strength tier is the
operator's policy choice; technical primitives are shipped.

**Detail**

**Failed second factors are throttled by Pryv (open-pryv.io
2.0.0-rc.27).** A per-account backoff, never a lockout
(open-pryv.io `6231a37c`, `aa445c43`): after
`services.mfa.attempts.backoff.freeFailures` failures (default 3)
within `perAccountWindowSeconds` (default 900 s), each further
failure delays the next attempt, doubling from `baseSeconds`
(2 s) up to `maxSeconds` (300 s); `mfa.verify` / `mfa.confirm` /
`mfa.challenge` answer 429 `too-many-attempts` with `Retry-After`
meanwhile, and a code sent during the delay is not checked. A
password holder cannot lock the real user out, and a success
clears the tally. The `attempts` block is platform-wide policy
(same values on every core); `backoff.maxSeconds: 0` disables it.

**Failed passwords are delayed too (open-pryv.io 2.0.0-rc.47).**
Sign-in, `account.changePassword`, the MFA step-up by password and
`mfa.recover` share a per-account tally
(`auth.passwordAttempts`: after 5 failures within 900 s, delays
from 2 s doubling up to 300 s, 429 with `Retry-After`, never a
lockout) `[CEPB1]`, plus a budget per client address counted across
all cores (`auth.passwordAttempts.perIp`, 30 failures per 900 s)
`[CEPI1]`; these methods answer `400` inside a batch call or over
socket.io `[CEDB1]`. Each password hash gets its own salt (bcrypt,
cost 10) `[PWSL1]`. SMS second factors carry send budgets per
session, per user, per destination across the platform and, since
2.0.0-rc.50, per core (`services.mfa.methods.sms.sendLimits`,
against toll fraud) `[MSSL1]`, `[MSSL11]`, and an account holds at
most `services.mfa.sessions.maxPendingPerUser` pending MFA logins
`[MCPU1]`; since 2.0.0-rc.51 a login refused after its MFA session
opened ends that session, so a failed login no longer holds one of
those places until it expires `[MLSX1]`.

**Password checks under load (open-pryv.io 2.0.0-rc.87).**
Password checks run at
most `auth.passwordCheckConcurrency` at a time per API worker
(default 2), `auth.passwordCheckQueue` waiting (default 50, at
most 10 s). A check refused past that is not performed: sign-in,
password change and reset, `mfa.recover`, the MFA step-up and
registration answer `429 too-many-requests` with `Retry-After`,
never `invalid-credentials`, and the refusal neither counts on the
account's failed-password tally nor delays the account `[PCLM1]`,
`[PCLM2]`; a refused registration leaves the name and email free
to retry `[PCLM3]`. OAuth client-secret checks answer `503
temporarily_unavailable`, never `invalid_client` `[OPCL2]`.

**Single-use codes and safe configuration.** A TOTP code is
consumed with a storage compare-and-set (open-pryv.io `43293101`,
`6231a37c`), so concurrent verifies of one code release exactly
one token; the per-session attempt ceiling counts parallel
attempts (`1d91696c`); and impossible `services.mfa` settings
refuse the boot (`214b0b2b`). The private profile shows the MFA
enrolment without its secrets and refuses writes to it
(`25239783`, `7ce9ea6f`); recovery codes are stored hashed
(`ef66853e`). Tests `[MA12A]`-`[MA12K]`, `[MBKF1]`-`[MBKF3]`,
`[PCS1]`, `[MCHK1]`. Since 2.0.0-rc.51 two concurrent activations
that both fail at the provider keep the enrolment that was pending
before them `[MACC2]`.

**Access tokens chosen by the caller (the release after
open-pryv.io 2.0.0-rc.89).** A token is a bearer credential.
`accesses.create` with an explicit `token` refuses one shorter
than 16 characters, measured after slugification (what is
stored), with `400 invalid-parameters-format` `[TKMN1]`; a token
Pryv generates (the `token` omitted) has 24 characters. Existing
accesses keep their tokens whatever their length: list the
accesses your integrations created with chosen tokens if you need
to replace short ones.

**Tokens Pryv generates come from the secure random source (the
release open-pryv.io 2.0.0-rc.90).** Access tokens (the
`token` omitted), personal (session) tokens, password-reset tokens
and the default token of a cross-account (CMC) access are drawn
from `node:crypto` directly, with no bias between symbols
`[SCTK1]`, `[SCTK2]`, `[SCTK3]`. Before, they came from an id
library that falls back to a non-cryptographic source
(`Math.random`) on a platform without a crypto API, so their
strength depended on that detection at run time. The shape is
unchanged (24 lowercase letters and digits, a letter first):
clients that check the format see no difference, and tokens
already issued stay valid. Record ids keep their own generator.

- tests: MFAA, MA15A, MA15C, MA3A, MA4A, MA5A, MA5B, MA6A, MA7A, MA10A, MA11A, MA12A, MBKF1, PCS1, MCHK1, CEPB1, CEPI1, CEDB1, PWSL1, MSSL1, MSSL11, MCPU1, MLSX1, MACC2, PCLM1, PCLM2, PCLM3, OPCL2, TKMN1, SCTK1, SCTK2, SCTK3
- config keys: services.mfa.mode, services.mfa.attempts.backoff, auth.passwordAttempts, auth.passwordAttempts.perIp, services.mfa.methods.sms.sendLimits, services.mfa.sessions.maxPendingPerUser, auth.passwordCheckConcurrency, auth.passwordCheckQueue

## ISO 27001 A.8.10: A.8.10 Information deletion

Coverage: configurable · effort saved: medium · draft

Requirement: Information stored in information systems, devices or in any
other storage media shall be deleted when no longer required.

**What Pryv does for you**

Per-user erasure: `system.users.delete` removes the user's data
from the live store. Engine-dependent backup behaviour (SQLite
per-user file vs PG row deletion + backup rotation)
determines whether erasure extends to backups, same notes as
GDPR Art. 17 + HIPAA-Security §164.310(d) media-controls. Event-
level and stream-level deletion live alongside for per-record
deletion needs. Since open-pryv.io 2.0.0-rc.47 the deletion also
erases the high-frequency series kept under the account's former
usernames and aliases (earlier releases could leave them), and
since 2.0.0-rc.50 points written during the deletion do not
survive it; see GDPR Art.17 for the full list.

**Detail**

Account auto-deletion, since open-pryv.io 2.0.0-rc.66
(`8521c8d5`, see gdpr.Art.5 §1(e) and gdpr.Art.17). Deleting a
whole account "when no longer required" is schedulable: by the
account holder (a date, or a period without use) or by your
inactivity preset, with reminder mails (`[ACXP3]`) and a minimum
notice (`[ACXP8]`) before, through the same erasure as
`system.users.delete`, guards included (`[ADSW8]`); an erasure
interrupted halfway is completed at a later pass (`[ADSW19]`).

Unfinished registrations (the release after open-pryv.io
2.0.0-rc.89; merged, unreleased at this walk). Rows a failed or
interrupted registration left behind are no longer required by
any account: a failed registration's compensation now removes
its account fields on PostgreSQL too `[URB2]`, and
`bin/reconcile-user-cores.js --registrations` lists, per core,
account fields under an id the users index lacks and indexed
accounts with no password, and deletes only with `--apply`
(orphan ids holding account fields alone, older than the grace;
a named account through the account deletion's erasure)
`[RCRG1]`, `[RCRG3]`; the default username pass releases the
email a stale name held on the platform `[RCRG6]`. See
gdpr.Art.5 §1(e) for the safeguards.

CMC retry rows left by erasures before open-pryv.io 2.0.0-rc.72
(open-pryv.io 2.0.0-rc.90). Each holds a
counterparty's invite URL with its token and is no longer required
by any account. `bin/reconcile-user-cores.js --cmc-retries` lists
them on PostgreSQL and deletes them only with `--apply`, for an id
that holds nothing else and has no erasure record `[RCCR1]`,
`[RCCR2]`; an empty users index facing such rows is refused
`[RCCR3]`. It replaces the manual query of the rc.72 notes; on
SQLite such rows stay in the erased account's kept directory. See
gdpr.Art.17.

Nothing stored after the deletion (the release after open-pryv.io
2.0.0-rc.89). Work still running for an account while it is
erased can no longer store data for it: on PostgreSQL the database
refuses a new row for an id the users index does not hold, and the
deletion's removal of the data sees any insert that was in flight
`[PGUG1]`, `[PGUG3]`; on SQLite with `audit.onUserDelete: keep`
the kept directory holds the audit files and an `erased.json`
marker only, and no new file is created there while the marker is
present `[CMCER4]`, `[ERMK3]`. Residual: one empty SQLite file in a
millisecond window, no row. See gdpr.Art.17.

Record of each deletion (open-pryv.io 2.0.0-rc.89,
`83e14c94`). Every account erasure leaves one
record in the platform database, the erasure ledger: keyed
hashes of the user id and username, when, what decided it, on
which core, no account content `[ERLG3]`, `[ERLG4]`; the
erasure is not finished until it is written `[ERLG6]`. It is
your evidence that information was deleted when no longer
required, read with the admin key (`GET /system/admin/erasures`,
`POST /system/admin/erasures/lookup`, `bin/erasures.js`)
`[ERLA2]`, `[ERLA4]`, `[ERLT1]`, and itself deleted after
`accountErasure.ledger.retentionDays` (default 1825; every core
purges the shared ledger with its own value, so the shortest one
set applies) `[ERLT4]`. A restore of a backup no longer brings
back an account deleted after it unless you pass
`--restore-erased` `[ERLR1]`, `[ERLR8]`, and `bin/erasures.js
--replay --apply` deletes again what a restore of the storage
itself brought back `[ERLT3]`. A change of the ledger key
disarms the lookup, the restore check and the replay for older
records unless the old key is kept; the lookup counts them
(`otherKeyRecords`) `[ERLA6]`. See gdpr.Art.17.

**Evidence**

- tests: USAD, DLN1, DLN4, DLLW1, ACXP3, ACXP8, ADSW8, ADSW19, URB2, RCRG1, RCRG3, RCRG6, RCCR1, RCCR2, RCCR3, ERMK1, ERMK3, PGUG1, PGUG6, PGUG9, ERLG3, ERLG4, ERLG6, ERLA2, ERLA4, ERLA6, ERLT1, ERLT3, ERLT4, ERLR1, ERLR8
- docs: customer-resources/account-auto-deletion.md, customer-resources/backup.md

## ISO 27001 A.8.13: A.8.13 Information backup

Coverage: facilitated · effort saved: medium · mode: infrastructure · draft

Requirement: Backup copies of information, software and systems shall be
maintained and regularly tested in accordance with the agreed
topic-specific policy on backup.

**What Pryv does for you**

`bin/backup.js`
produces per-user backup files, the only copy of user data Pryv
makes; a multi-core cluster replicates the platform DB only
(rqlite Raft + mTLS), not user data, which stays on each user's
home core. The operator's
backup policy (cadence, retention, offsite) is layered on top;
for an offsite copy in another country or with a provider, see
"Offsite copies" in the detail.
"Regularly tested" is the operator's drill. On the Pryv side,
backup and restore round trips are tested: `[BKSR]` (series
data), `[BKEV]` (events store), `[BKVR]` (manifest version), and
`just test-backup-roundtrip` in open-pryv.io backs a seeded user
up and restores it PostgreSQL to SQLite and back, comparing the
bundles on counts and content (2.0.0-rc.34).

**Take a new backup after upgrading to open-pryv.io 2.0.0-rc.34
or later.** Earlier `bin/backup.js` backups carry no
high-frequency series data on any series engine, with no
warning, and series backed up from InfluxDB could not be
restored. Since 2.0.0-rc.34 the series are exported and restored
and move between any two series engines.

**Check every directory that received `bin/backup.js
--incremental` before open-pryv.io 2.0.0-rc.51.** Such a run
overwrote the full backup it continued; the directory holds only
the last delta and cannot be repaired. `--inspect <dir>` reports it
`DAMAGED` and `--restore` refuses it `[BKIC2]`, `[BKC6]`: take a
new full backup into a new directory. Since 2.0.0-rc.51 the
incrementals form a chain next to the full backup (detail below).

**From open-pryv.io 2.0.0-rc.86, write three points into your
backup policy.** A backup written by 2.0.0-rc.86 or later restores
with that release or later; after going back to an earlier
release, start a new chain in a new directory `[BKSM6]`. Keep each
backup directory for the backup only (a file the backup did not
write is refused at restore) `[BKSM7]`, `[BKSM8]`. Sign the runs of
a recipient-key backup (`--signing-key` / `--signing-pubkey`),
starting with a new full backup into a new directory.

**Detail**

**Backup encryption is built in, opt-in** (open-pryv.io
2.0.0-rc.5 onward). Without flags `bin/backup.js` writes
plaintext (gzip-compressed) files. `--recipient-pubkey <pem>`
(recommended: the per-backup data key is RSA-OAEP-wrapped to
your public key, so the backup host cannot decrypt its own
output) or `--encrypt-passphrase` / `PRYV_BACKUP_PASSPHRASE`
(scrypt) encrypts every file with per-file authenticated
AES-256-GCM before it reaches the destination, and the backup
ships a standalone `decrypt-backup.mjs` plus `RESTORE-README.md`
for recovery without Pryv. A.8.13's "protected at the same
security level as the source data" expectation is met by
enabling one of the two key models, or by your own layer
(LUKS / S3 SSE-KMS / ...) on a plaintext backup; record the
choice and the key custody (a lost key or passphrase makes the
backup unrecoverable) in your backup-policy SOP.

**Offsite copies.** Pryv writes backups to a directory and never
uploads or expires them: destination, transport, access control
and retention of the offsite copy are in your policy. Encryption
with a key the provider never holds protects the content there;
it does not settle the legal side (a provider that only stores
encrypted data is a processor, storage in a third country is a
transfer to assess), and an encrypted backup still shows user
ids, run dates, file counts and sizes. Put the destination in
your supplier and data-protection registers, keep the decryption
key out of the provider's reach, and test restores from the
offsite copy itself: `context/encrypted-offhost-backups.md`.

**Since open-pryv.io 2.0.0-rc.47 to 2.0.0-rc.50**: a plaintext
backup is announced on stderr `[BKPW1]`; `--passphrase-file` keeps
the passphrase out of the process list `[BKPF1]`; backups are
written owner-only (`0700` / `0600`); a restore refuses an
unexpectedly plaintext backup `[BKRE1]` (`--require-encrypted` makes
that the rule `[BKRE4]`), unsafe names and symbolic links `[BKRS1]`,
`[BKRS4]`, reserved names `[BKRN1]` and a username another account
now holds `[RSOW1]`. Recipient-key encryption gives confidentiality,
not authenticity: protect write access to the backup destination
(and, from 2.0.0-rc.86, sign the runs, below).
See `context/operator-backup-coverage.md`.

**Incremental chain (open-pryv.io 2.0.0-rc.51).** Each
`--incremental` run writes its own `incrementals/<runId>/`
directory, listed in `chain.json`, and rewrites no earlier file
`[BKC1]`; a restore applies the full backup then each run in order,
deletions included `[BKC2]`, `[BKIC1]`, and `--through-run <runId>`
restores as of a given run `[BKC7]`. Runs no longer miss changes
made while the previous run was in progress `[BKC3]` and carry the
deletion of streams, accesses and webhooks `[BKC4]`. Each run of an
encrypted backup has its own envelope and key under the chain's key
model, plus its own decrypt script `[BKC5]`, `[BKCS1]`. Overlapping
runs into one directory keep the first and set the second aside
`[BKCC1]`. A whole-core run records the accounts it covers, so a
restore does not re-create an account deleted between runs
`[BKCU1]`, `[BKIC4]`. The A.8.13 "regularly tested" drill should
include a chain restore and `--inspect` of the chain you rely on.
Up to 2.0.0-rc.85 the chain index and run manifests are checked for
consistency, not signed.

**Authenticated files and signed runs (open-pryv.io 2.0.0-rc.86).**
Each run's manifest lists every file with its size and SHA-256
hash and is bound to its run; a restore refuses a file added,
removed, resized or changed and a `chain.json` entry that disagrees
with the run's manifest `[BKSM1]`, `[BKSM2]`, `[BKSM3]`. Encrypted
files end with a marked final block, each block tied to its file,
position and run, so truncation at a block boundary, an emptied
file or a file swapped between accounts is refused; an account's
files are checked before anything of it is written. Optional
Ed25519 run signatures (`--signing-key` at backup,
`--signing-pubkey` at restore and `--inspect`) close the
recipient-key bound above: given the public key, every run must be
signed by it `[BKSM4]`, `[BKIS1]`; an unsigned recipient-key backup
prints a warning `[BKSM5]`, `[BKIS2]`. For the "regularly tested"
element, `--inspect --verify-files` (with the backup's secret)
reads and checks every file without restoring `[BKIS3]`. New
passphrase backups use scrypt N = 2^17. Runs written by earlier
releases restore as before, reported as "file list not verified";
a plaintext run's file table detects corruption, not tampering. An
account erased during a full backup is left out of the run
`[BKDU1]`, and an account whose restore fails while its data is
written is cleared and removed from the core's index instead of
being left half-restored `[RSFC1]`, `[RSFC3]`. Operator page:
`customer-resources/backup` on the developer site.

**External ids (open-pryv.io 2.0.0-rc.58).** The platform backup
carries the external-id namespace rows with their salts; a restore
keeps a live namespace whose salt differs and reports it `[XIDB1]`.
The index rows are rebuilt by `bin/reconcile-user-cores.js
--ext-ids` on each core. The accounts' own links (the core's local
external-id table) are not in the per-user backup in 2.0.0-rc.58
and 2.0.0-rc.59: include that table in your database-level backup
of each core and in the restore drill. See
`context/operator-backup-coverage.md`. From 2.0.0-rc.60 the per-user backup carries
each account's ids (`users/<userId>/external-ids.jsonl[.gz]`:
namespace, blinded value, claim date), also in incremental
chains; a restore links them again after the platform rows, an
id another account holds by then stays with it and is counted
`lost`, an id of an unknown namespace is `skipped` `[XIDB2]`,
`[XIDB3]`, `[XIDB4]`, `[XIDBK1]`, `[XIDBK2]`. A blinded value can
claim its id, so a per-user backup becomes as sensitive as a
claim credential: encrypt it (see above). An account rolled back
by `--verify-integrity` keeps its restored ids; release them with
the admin release if the account is to be dropped.

**Account aliases (open-pryv.io `4547b32a`, 2.0.0-rc.66).** Earlier backups did not carry an account's aliases
(access aliases, former usernames): after a restore its aliased
accesses and endpoints under a former username did not route and a
former username could be registered by someone else. From that
release the per-user manifest lists them (`aliases`) and the restore
reserves them again; an alias another account or core holds by then
stays with it and is reported `[BKAL1]`. Series still held under a
former username are exported and restored under the username
`[BKAL3]`. Take a new backup after upgrading.

**Erased accounts stay erased (open-pryv.io 2.0.0-rc.89,
`83e14c94`).** A restore checks the erasure ledger
(one durable record per erased account, see gdpr.Art.17): an
account erased after its backup is not restored, whether the
ledger records it (and no restore since) or an erasure of it
started on the core after the backup is unfinished; an account
that still exists gets the usual `--overwrite` refusal first. A
whole restore lists the erased accounts under "Erased after this
backup" and restores the others (exit code 3 when it restores
nothing else), a `--user` restore of one fails `[ERLR1]`,
`[ERLR3]`, `[ERLR8]`; a restore that cannot build the ledger key
is refused `[ERLR7]`. `--restore-erased` restores the account
and marks its record restored `[ERLR2]`, only once
`--verify-integrity`, if given, kept it `[ERLR6]`; a mark that
fails is listed and the restore exits 4 `[ERLR9]`. A chain dates
each account by the newest run that holds it `[ERLR5]`. The
platform backup carries the ledger and a restore merges it
without removing anything `[ERLR4]`. Include in the drill: after
restoring a core's storage itself (volume snapshot, database
dump), `bin/erasures.js --replay` lists by id the accounts it
brought back that were erased since, and `--apply` erases them
again `[ERLT3]`; check the list first (an account behind an exit
4 is in it). Keep `accountErasure.ledger.retentionDays` the same
on every core (the shortest applies) and at least as long as
your longest backup retention, and keep the ledger key across
admin-key rotations: a purged record, or one under an older key,
no longer stops a restore.

## ISO 27001 A.8.15: A.8.15 Logging

Coverage: implemented · effort saved: high · draft

Requirement: Logs that record activities, exceptions, faults and other
relevant events shall be produced, stored, protected and
analysed.

**What Pryv does for you**

Per-user audit log captures the API calls on an account (scope in
the `audit` primitive; calls without a user go to the syslog
mirror, off by default); access reference (accessId + accessSerial) ties each row to the
authenticated identity. Since open-pryv.io `07b6d3b6` this
includes the OAuth2 authorization server's own activity
(`oauth.*` events: consent lifecycle, code exchange incl. replay
attempts, token issued / refreshed / revoked / reuse-detected),
authorization decisions are logged alongside the data accesses
they enable. Audit storage has its own storage interface (per-user
SQLite files, or its own PostgreSQL connection pool) to decouple
the log from data-path engine issues. A failed audit write never
changes the call's answer and is logged at error level for the
operator's alerting `[BAUF1]`; from the release after open-pryv.io
2.0.0-rc.89 it is also counted, for the same alerting (see
hipaa-security 164.312(b)); it is not recovered. The
"analysed" element (review cadence, alerting thresholds) is the
operator's procedure.

**Detail**

**OAuth2 events added in open-pryv.io 2.0.0-rc.66 to 2.0.0-rc.77**:
`oauth.nonce.reused`, `oauth.token.exchanged` (subject's trail),
`oauth.consent.refused` reasons including
`audience-account-mismatch` and `issuer-account-mismatch`;
`oauth.token.introspected`, `oauth.token.exchange_refused`,
`oauth.client.metadata_fetched` / `metadata_refused` (syslog, no
user resolved; never a token or a document body) `[OXN02]`,
`[OXI06]`, `[OTX03]`, `[OCMDE13]`, `[OPIU3]`. Adapter-route
requests are not audited by the core. Since rc.77 a streamed
answer the client stopped reading is logged as an error
(`client-closed-request`), not a success `[AUAB3]`. From the
release after rc.89, calls running at the same time on one
socket.io connection are each audited under their own method;
before, two such calls could swap their method id in the audit
row and the access usage counts `[SKMC]`. Full list on
`hipaa-security.164.312(b)`.

**From open-pryv.io 2.0.0-rc.90**: the creation
of an account is the first record of its own trail
(`account.created`, type `audit-log/account`, ids and fixed words
only) `[AACR1]`, `[AACR3]`, `[AACR4]`; a filter listing methods one
by one must add it, `account.all` and `all` select it `[AACR7]`.
An audit filter entry `<group>.all` whose group is not a whole name
(`a.all`, `callBatch.all`) refuses the boot instead of selecting
nothing behind a warning `[AFGW]`, so a typo can no longer switch a
log off silently.

**Analysis by the account owner (open-pryv.io 2.0.0-rc.84).**
The owner's `accesses.get` reports, per access, approximate
lifetime call counts by method (`usage`; never returned to an app
or shared caller) `[AUG1]`, `[AUG3]`, and the reference account
app (app-web-user-account 0.34.0) adds a linkable, filterable
Audit trail tab over the account's audit log. Since rc.86 the
owner can also have that log counted per hour, day or week over a
period (`audit.getSummary`, refused to app and shared callers)
`[ASM1]`, `[ASM4]`. This helps your
users review their own activity; the operator-side analysis
(review cadence, alerting) stays yours. Detail on
`hipaa-security.164.312(b)`.

"Stored, protected" caveat, the audit log is append-only by
convention in the write path, but there is **no software-side
tamper-resistance signal** (no hash chain, no per-row
signature, no operator-signed checkpoint). Protection of the
log rests on the operator's filesystem hardening: immutable
mounts, append-only flags (`chattr +a`), file-integrity
monitoring (AIDE / Tripwire), out-of-band SIEM forwarding to
a WORM store.

Future direction: chained / signed audit log (per-row prev_hash
+ periodic operator-signed checkpoints). Tracked under internal
backlog slug `AUDIT-LOG-CHAINING` and
`proposals/audit-log-chaining.md`. When shipped this row's
coverage stays Implemented but the cited primitives will
include `audit-chain`.

Separate audit property worth flagging to the A.8.15 auditor:
Pryv's audit log is data-minimal by construction, it captures
action + source + URL query + access ref + integrity hash, but
**never the request body**. The log itself therefore qualifies
as well-scoped under the "logs that record activities" framing
without storing the data being acted on. Caller-supplied search
values (`events.get` content-query conditions on the GET path)
do appear in the recorded URL query, see
`context/content-query-audit-semantics.md`. See
`docs/pryv-primitives.md` audit entry for the full capture
catalogue.

**Server logs are protected from carrying credentials (open-pryv.io
2.0.0-rc.43 to 2.0.0-rc.50).** The operational logs (`logs.file`,
`logs.fileSync`, console, `DEBUG=pryv:*`) are separate from the audit
log, and they are what a log shipper or a support engineer reads.
Credential values are masked wherever they are logged, including
inside a logged `Error` (message, stack, cause) and the debug output;
the masked names cover access and refresh tokens, passphrases, the
admin key and the platform secrets; URL user info, access-request
keys, `readToken`, `key` / `poll` and authorization-code `code` /
`state` values are hidden; a parameter validation error is logged
without the rejected value; the request trace prints no Basic-auth
user name `[BLGM1]`, `[BLGM2]`, `[BLGM3]`, `[BLGM4]`, `[RDL5]`,
`[RDL8]`, `[RDLA]`, `[RAL1]`. A server-side fault is answered to the
client as `Unexpected error (ref <8 hex>)`, its detail logged under
the same reference `[UNXR1]`. The boot log identifies the admin key
by a keyed fingerprint, not a hash a log reader could test
candidate keys against `[PLFP1]`. Log files are created `0640`, and
the log directories the core creates `0750` (2.0.0-rc.50; existing
files and directories keep their modes)
`[BLFM1]`. Check the retention of logs written by releases before
2.0.0-rc.43, which may hold credential values; log shipping,
retention and access to the log host stay yours.

**External ids** (`external-id-index` primitive): an
administrator's release of an id claimed by the wrong account
(from 2.0.0-rc.60) is
logged on the admin side without a user (syslog) and, when audit
is active, in the trail of the account that held it
(`account.externalIds.adminRelease`: namespace and reason)
`[XIDAR1]`, so the subject's own history shows the operator's
act. The blinded value reaches no audit row and no server log
`[XIDG1]`. The credential-free lookup and the core-to-core holder
answer of forced-mode sign-ins (`system.extIdHolds`, 2.0.0-rc.59)
are not audited.

**Long-running deployment tiering**: for the "logs … stored,
protected, analysed" portion of A.8.15 at multi-year scales,
the audit log is exposed via the `@pryv/datastore`
abstraction. Operators write a custom `auditStorage` engine
plugin to tier hot recent rows + cold archived rows (e.g.,
S3 Object Lock, Glacier) behind the same `audit.getLogs`
API. No Pryv-shipped pruning primitive, pressure to prune
is operational, not regulatory (HIPAA-style retention floors
apply; there's no max-retention rule pushing destruction).
Full pattern at
`context/audit-archival-via-custom-datastore.md`.

- config keys: logs.file, logs.fileSync

## ISO 27001 A.8.20: A.8.20 Networks security

Coverage: configurable · effort saved: medium · draft

Requirement: Networks and network devices shall be secured, managed and
controlled to protect information in systems and applications.

**What Pryv does for you**

TLS in transit once configured: either the core terminates it
(`http.ssl.*`, with the built-in ACME integration issuing,
renewing and replicating certificates across the cluster when
`letsEncrypt.enabled` is set) or your reverse proxy does and the
core serves plain HTTP behind it (default `http.ip` 127.0.0.1).
Between cores, Raft runs over mutual TLS on a private cluster CA
once `bin/bootstrap.js` has written `storages.engines.rqlite.tls`
(default `tls: null`, plain TCP). The core sets no TLS version of
its own: Node.js defaults apply (TLS 1.2 floor on the Node 24 the
image runs). Operator-side network controls (firewalls, network
segmentation) sit on top.

**Detail**

When a proxy in front of the core terminates TLS, set
`hostedSites.<name>.hsts: always` on each HTTPS-only site the
core hosts so its answers carry `Strict-Transport-Security`
(open-pryv.io 2.0.0-rc.34). The default, `auto`, sends the header
only when the core itself terminates TLS; `never` turns it off.
The core does not add HSTS to API answers on a separate API
host, so set it on your proxy there.

Outbound side (open-pryv.io 2.0.0-rc.56): the calls Pryv makes
to URLs a counterparty supplies (cross-account consent
deliveries, chat, revocations, scope updates, delegation and
OAuth revocation notices) cannot be turned toward your internal
network. A host that is or resolves to a loopback, private,
link-local or otherwise reserved address is refused before any
connection, and checked again at connect time `[PFR1]`, `[PFR2]`,
`[CO22]`; plain `http:` is refused unless
`cluster.allowInsecurePeerUrl` (development and test clusters)
`[PFR4]`. The platform's own host names are always allowed; list
peers on a private network, and a private `core.url` given as an
IP, in `cmc.allowedPrivateHosts` (host names, IPs or CIDR ranges,
the grammar of `webhooks.allowedPrivateHosts`; checked at boot)
`[PFR3]`. Webhook deliveries apply the same address rules. Egress
filtering on your network stays yours. From the release after
open-pryv.io 2.0.0-rc.89 webhook calls are signed with a
per-webhook secret (`Pryv-Signature`, HMAC-SHA256 of a timestamp
and the body), so the receivers on your side can refuse calls
that do not come from the platform `[WHSG2]`, `[WHSR1]`; webhooks
created earlier stay unsigned until `webhooks.rotateSecret`
`[WHSG6]` (see `context/webhooks-signal-only.md`).

**Inter-core certificates (the release after open-pryv.io
2.0.0-rc.89).** A newly created cluster CA is a CA that may sign
end-entity certificates only (`basicConstraints CA:TRUE,
pathlen:0`; key usage limited to signing certificates and CRLs)
`[CLCX1]`. The node certificate a core receives when it joins is
marked as an end entity (`CA:FALSE`), for digital signature and
TLS server and client authentication only, so a node's key cannot
sign a certificate another core would accept `[CLCX2]`,
`[CLCX3]`; the core id, hostname and address given for it must be
plain DNS names and an IP address `[CLCX4]`. Certificates already
issued and existing CAs are unchanged: a cluster created on an
earlier release keeps its CA and the node certificates it issued.

## ISO 27001 A.8.24: A.8.24 Use of cryptography

Coverage: implemented · effort saved: high · draft

Requirement: Rules for the effective use of cryptography, including
cryptographic key management, shall be defined and implemented.

**What Pryv does for you**

TLS for transit (in the core when `http.ssl.*` / `letsEncrypt.*`
is configured, otherwise in your proxy; the core sets no TLS
version of its own, so Node.js defaults apply, a TLS 1.2 floor on
Node 24), AES-256-GCM for at-rest operator secrets
(HKDF-derived per-key with purpose labels), AES-256-GCM
(scrypt-derived) for bootstrap bundle encryption, per-file
AES-256-GCM for `bin/backup.js` output when encryption is
requested, and, from open-pryv.io 2.0.0-rc.86, optional Ed25519
signatures of backup runs. The operator's
cryptography policy (key custody, rotation cadence, algorithm
choice for engine-side at-rest encryption) is layered on top.

**Detail**

**Changes in open-pryv.io 2.0.0-rc.86.** Backups: encrypted files
carry authenticated data naming their file, run and chain, with a
marked final block; each run's manifest lists every file's
SHA-256 hash; `--signing-key` (Ed25519) signs each run and
`--signing-pubkey` makes the signature mandatory at restore
`[BKSM4]`; new passphrase backups derive their key with scrypt
N = 2^17. Add the signing key pair to your key inventory: the
private key stays on the backup host, the public key with the
restore secret. Bootstrap bundles: the version, salt and nonce are
authenticated, with a pinned 16-byte tag `[BNEV1]`. Keys stored
encrypted at rest (TLS and ACME keys, authenticator secrets,
observability credentials, transfer identities): a second
envelope version, bound to the row that holds it and with a
pinned tag, is read from this release `[AREV1]`, `[AREV2]`;
2.0.0-rc.86 to rc.89 still write rows in the first version (no
binding) so that a core of the previous release can read them. The
release open-pryv.io 2.0.0-rc.90 writes version 2 `[AREV3]`:
every core must have run 2.0.0-rc.86 or later before it is
deployed, and going back to a release before 2.0.0-rc.86 is not
possible without restoring the rows. The configured
`letsEncrypt.atRestKey` is unchanged.

**Changes in open-pryv.io 2.0.0-rc.90.** Random
secrets: the bearer tokens Pryv generates (access, personal and
password-reset tokens, the default token of a cross-account
access) are drawn from `node:crypto` without bias, never from a
`Math.random` fallback `[SCTK1]`, `[SCTK2]`; same 24-character
shape, see A.8.5. Inter-core PKI: a newly created cluster CA
carries `basicConstraints CA:TRUE, pathlen:0` and signs only
certificates and CRLs `[CLCX1]`; node certificates state their
purpose (end entity, digital signature, TLS server and client
authentication) instead of leaving it to each verifier's defaults
`[CLCX2]`, `[CLCX3]`, see A.8.20. Existing CAs and certificates are
not reissued: record in your key inventory which clusters still
run a CA created before this release. Webhook signing: each
webhook created from this release has its own secret (`whsec_`
and 32 bytes from `node:crypto`) `[WHSG8]`, used as an
HMAC-SHA256 key over a timestamp and the body of each call
`[WHSG1]`. It is stored in clear with the webhook, like the
access token, travels with server backups `[WHSR5]`, is shown to
the client once, and is replaced with `webhooks.rotateSecret`
(no overlap window); its custody on the receiving side is your
integrators'.

## ISO 27001 A.8.9: A.8.9 Configuration management

Coverage: facilitated · effort saved: medium · mode: evidence · draft

Requirement: Configurations, including security configurations, of hardware,
software, services and networks shall be established, documented,
implemented, monitored and reviewed.

**What Pryv does for you**

Pryv configuration lives in
`default-config.yml` + `override-config.yml` + `host-config.yml`
(operator-side); a `config-validation` step on master start
fails fast on unresolved variables or missing required service
fields, giving a baseline "configuration is well-formed" check.
From open-pryv.io 2.0.0-rc.90 (`21fd8085`)
the configuration is readable and comparable (per-core and
platform digests) without host access:
`GET /system/admin/config/effective` (admin key) answers what
each core runs with, secrets redacted. The operator's
config-change procedure (versioning, approval, deployment) and
the review sit on top. Audit log shows when config-driven
behaviour changed observably.

**Detail**

**Reading and comparing the configuration** (the release after
open-pryv.io 2.0.0-rc.89, `21fd8085`; developer site, system
reference, "Get the effective configuration"):
  - One entry per key, sorted, with the layer that set it
    (`default-file`, `base-file`, `override-file`,
    `bootstrap-file`, `env`, `argv`, `derived`,
    `platform-db`, ...) and its scope: `platform` (expected
    identical on every core) or `core` (differs by design:
    host, ports, paths, local credentials, local tuning)
    `[CFE1]`, `[CFC1]`. Every key of the shipped defaults has
    an explicit rule `[CFC1]`; a key no rule names is redacted
    as `unclassified`.
  - Two SHA-256 digests: `platform`, over the `platform` keys,
    to detect drift between cores; `full`, over every key, to
    compare a core with its previous baseline. They ignore
    order and sources and recompute from the returned keys
    `[CFE6]`, `[CFC8]`; `?digest=true` answers the digests
    only, for a cheap periodic check `[CFE3]`. A changed secret
    changes the digests through its keyed fingerprint, without
    revealing it; with no usable `auth.filesReadTokenSecret`
    there are no fingerprints (`configMeta.secretFingerprints:
    false`) and a changed hidden value does not change them.
  - Secrets never shown (presence, type and fingerprint only)
    `[CFE5]`; each read is audited without a user, logged and
    never cached `[CFE8]`.
What stays yours: the approved baseline itself, storing the
snapshots, the review cadence and the change procedure; the
host, OS, network, proxy and database-server configuration,
which this document does not cover; and the values the master
process alone sets, which are not in it (it is the view of the
API worker that answers). It shows configuration, not that a
control is effective.

**Evidence**

- tests: CFE1, CFE3, CFE5, CFE6, CFE8, CFC1, CFC8
- primitives: audit

## ISO 27001 A.8.11: A.8.11 Data masking

Coverage: facilitated · effort saved: medium · mode: primitive · draft

Requirement: Data masking shall be used in accordance with the organization's
topic-specific policy on access control + other related topic-
specific policies, and business requirements, taking applicable
legislation into consideration.

**What Pryv does for you**

Pryv enforces masking by **projection**, not transformation:
stream-level isolation + permission-scoped access tokens hide
whole sub-trees from a given role. The "rewrite a value before
display" flavour of masking (e.g., `j***@example.com`) lives in
the calling application, by design.

**Detail**

The boundary is recorded in
`context/data-masking-projection-vs-transformation.md`:
  - Stream-tree split + narrow access tokens = Pryv's
    projection-side contribution. Auditor-visible via the
    access permissions matrix.
  - Field-substring rewrites, hash-on-read, faker substitution,
    per-role redaction = application layer. Not Pryv's job by
    design (storage layer stays deterministic; "partially
    redacted" is not an API response).
  - Username-side pseudonymisation is the one transformation
    Pryv does natively: `accesses.create {randomAlias:true}` mints
    a routable `r-XXXXXXXX` alias that hides the username per access
    (`proposals/aliases-as-pseudonymization-primitive.md`); it
    survives a backup and restore and routes on every topology
    since open-pryv.io `4547b32a`. It masks the username from the
    holder, and since open-pryv.io 2.0.0-rc.69 the token is
    accepted under its alias only, so a holder who guesses the
    username cannot confirm it with the token (`[AL13]`,
    `[OPSE5]`; earlier releases accepted it under every name of
    the account).
  - Third-party record ids are masked before they reach Pryv
    (open-pryv.io 2.0.0-rc.58, `external-id-index` primitive): your
    service sends `HMAC(K_namespace, recordId)` with a key it keeps,
    the platform index stores a token of it mapped to a core, and
    no listing, error, log line or audit record returns the value
    `[XIDC1]`, `[XIDC7]`, `[XIDG1]`, `[XIDN4]`. Key custody is
    yours: every holder of `K_namespace` can look up and claim ids
    of that namespace.
  - Client addresses and emails in the keys Pryv stores its
    abuse budgets and registration email challenges under
    (failed-password and password-reset budgets per address,
    the `/reg/access` creation budget, the email challenge rows
    and verification-mail slots in the platform database; the
    per-address budgets of the unauthenticated lookup routes and
    the mail budgets in each core's cluster store) are an
    HMAC-SHA256 under a key derived from
    `auth.adminAccessKey` from the release after open-pryv.io
    2.0.0-rc.89 `[SKHA1]`..`[SKHA4]`. Earlier releases stored a
    plain SHA-256, which a listing of the platform database
    reverses by enumerating addresses or running a mailing list
    through it; the keyed hash leaves that to holders of the
    admin key.
  - Static masking for non-prod environments + field-level
    encryption at the schema layer are both implementer
    concerns today; end-to-end encryption
    (`proposals/e2e-encryption.md`) is the natural future
    primitive for both.
  - The audit log itself is data-minimal by construction,
    captures action + access + integrity hash, never the
    request body (see `docs/pryv-primitives.md` audit entry).

**Evidence**

- tests: XIDC1, XIDC7, XIDG1, XIDN4, AL13, OPSE5, SKHA1, SKHA2, SKHA3, SKHA4
- primitives: randomAlias, stream, system-streams, event, external-id-index
- context notes: data-masking-projection-vs-transformation

## ISO 27001 A.5.16: A.5.16 Identity management

Coverage: implemented · effort saved: high · draft

Requirement: The full life cycle of identities shall be managed.

**What Pryv does for you**

Pryv's account + access primitives implement the full identity
lifecycle: create (registration), enable (login + access mint),
modify (accesses.update, account.update), suspend (access
narrowing), terminate (accesses.delete + system.users.delete).
Audit log gives the per-stage evidence. The naming + assignment
policy is the operator's.

**Detail**

For workforce / role-scale deployments, Pryv composes with an
external IdP / IGA system via two patterns documented in
`context/workforce-access-patterns.md`: (1) group access +
`callerId` audit suffix, (2) seed access + sub-access
derivation. **Roles + groups themselves are deliberately
outside Pryv;** the IdP is the source of truth for identity
lifecycle, and Pryv records the resulting access state +
per-individual audit trail. A third pattern ships in
open-pryv.io 2.0.0-rc.53 (release commit `61fb28dd`,
https://github.com/pryv/open-pryv.io/issues/158): for a team
sharing one account that reaches patient data through
cross-account consent, each member is their own Pryv account,
joins through a membership request an administrator of the group
approves `[GA01]`, acts on patient accounts under accesses the
group's core issues and the patient's core stamps with their
identity `[GA10]`, and leaves (or is removed, including when the
delegate who approved them is detached) with those accesses
swept by the platform `[GA20]`, `[GA21]`, `[GA23]`. Roles stay
outside Pryv in that pattern too: a team is a stream, a
membership is a consent relationship. See
`context/workforce-access-patterns.md`, Pattern 3.

**Delegated-app identity via OAuth2.** For app identities, Pryv
ships an OAuth2 authorization-code + PKCE flow
(`open-pryv.io/components/oauth2/`, open-pryv.io 2.0.0-rc.8): each
client is a curated identity the operator registers through
`bin/oauth-client.js` (create / rotate-secret / list, the full
credential lifecycle), authenticating with mandatory PKCE (S256
only) against an exact-match registered redirect-URI set. Open
self-registration is disabled, so every client identity is
operator-authorised before it exists. Since open-pryv.io
2.0.0-rc.74 that holds while `oauth.clientMetadataDocuments.mode`
is `off` (the default); otherwise a client may identify itself by
an https URL on a host your policy accepts, with its reach set by
your template only (see `soc2.CC6.2`) `[OCMDE06]`.

**Identities an app sees (open-pryv.io 2.0.0-rc.68 to
2.0.0-rc.77).** An operator-registered client declares a subject
type, `public` or `pairwise`, with no default. A pairwise client
sees each user as a pseudonymous alias, one per user and client,
never the username, in token responses, the OpenID Connect id
token (`sub`, signed with a key of `oauth.signingKeys`) and
introspection `[OPSE1]`, `[OXD08]`; a public one sees the user's
internal id, also never the username. The account holder can mint
up to 10 address aliases (rc.76, personal token only, names chosen
by the server) that a consent can adopt as the app's address
`[OPAL1]`, `[OPAL2]`, `[OPUE9]`. Changing a grant's subject type
must be acknowledged by the user `[OCMP11]`. With
`oauth.perUserIssuer` (rc.77, opt-in) each account host is its own
OAuth2 issuer `[OPIS5]`.

**Delegate-account identity lifecycle.** Account delegation
(`open-pryv.io/components/delegation/`) manages the lifecycle of a
delegate relationship between two accounts: a controlled-account-
initiated invite / accept handshake creates it (create-from-
delegate can provision the controlled account itself, optional
email/password seed), an owner-equivalent delegate token enables
it, and an authoritative detach terminates it, reserved to a
genuine login on the controlled account (a delegate can never
remove a delegation). Each delegate acts under its own
attributable token, audited on the controlled account (same-core
+ cross-core), and `accessInfo` names the acting delegate. See
`context/delegation-model.md`.

App identities a delegate authorizes for the controlled account
carry that lineage for their whole life: `accessInfo` reports
them as granted through the delegation (`grantedVia: 'app'`,
naming the delegate) `[DCH02]`, and they end with the delegation
`[DCH12]`. In open-pryv.io 2.0.0-rc.23.

- tests: AA01, AA02, ACCP, UZEV, DCH02, DCH12, CMCGA, GA01, GA10, GA20, GA21, GA23, OCMDE06, OPSE1, OXD08, OPAL1, OPAL2, OPUE9, OCMP11, OPIS5
- config keys: oauth.clientMetadataDocuments.mode, oauth.signingKeys, oauth.perUserIssuer

**Detail**

**OAuth2 token + secret handling.** Where you delegate access to
apps, Pryv's OAuth2 flow (`open-pryv.io/components/oauth2/`,
open-pryv.io 2.0.0-rc.8) manages the authentication material for
you: access tokens are short-lived (`oauth.accessTokenTTL`,
default 1 h), refresh tokens are single-use and rotate on every
exchange with a sliding TTL bounded by an absolute cap
(`oauth.refreshTokenTTL` / `oauth.refreshTokenAbsoluteTTL`), and a
replayed (already-rotated) refresh token fails the exchange
(`open-pryv.io/components/oauth2/src/grants/refresh_token.ts`).
Confidential clients hold a rotatable `client_secret`
(`bin/oauth-client.js rotate-secret`). The operator's broader
secret-distribution + rotation programme stays the organizational
half; Pryv supplies the short-TTL + rotation mechanics.

**Since open-pryv.io 2.0.0-rc.69 to 2.0.0-rc.74.** A refreshed
token's predecessor expires after `oauth.refreshRetireGraceSeconds`
(default 60 s) `[ORET1]`; a refresh refused for bad client
authentication no longer uses up the refresh token `[ORL04]`; audit
rows name refresh tokens by a hash, never by their first
characters `[ORL12]`. Per-client lifetimes may only shorten the
platform's (rc.70); a rotated secret can stay valid for at most 30
days `[OCAK14]`. `private_key_jwt` assertions are checked only
with a key of their type and a pinned algorithm, a multi-key set
needs a `kid` on each key, and a `jwks_uri` is fetched through the
outbound guard `[OCAK2]`, `[OCAK7]`, `[OCAK23]`. The OpenID Connect
signing keys (`oauth.signingKeys`) and the per-core keys that sign
the consent flow's and third-party sign-in's browser state
(`oauth.stateKey`, `sso.stateKey`, required since rc.70, no longer
derived from the admin key) live in the YAML configuration, never
in the platform DB `[OXK01]`, `[OXSK1]`, `[CKOC2]`.

**Transmitting authentication information to a third party.**
"Appropriate handling" includes how a credential travels when you
hand it to someone else. Pryv's shared-secrets endpoints
(`open-pryv.io/components/shared-secrets/`) replace the
URL-embedded-token pattern with a one-time random key: redeemable
exactly once, mandatory TTL, only the SHA-256 of the key's random
half stored server-side, payload scrubbed when the item leaves
the pending state (on redemption, on a signature mismatch, and on
the first retrieval attempt after the TTL; expiry is enforced on
access, not by a background sweeper, so an untouched expired
secret keeps its payload until something reaches it or you delete
it), optional passphrase / HMAC signature on redemption. Your handling policy
("never send credentials in links or logs") gains a shipped
mechanism to point at instead of a prohibition alone. A
`secretSharing: forbidden` feature permission, inherited by
child accesses, lets you exclude publicly-exposed tokens from
the mechanism entirely. The same one-time-key mechanism carries the
session token when an account holder signs in through an external
OpenID Connect provider (`sso.*`, beta, off by default): the token
is never placed in the redirect URL, and the federated login is
gated so an external identity cannot claim an account whose email
was never inbox-proved.

**Strength of chosen access tokens.** From the release after
open-pryv.io 2.0.0-rc.89, a token chosen by the caller of
`accesses.create` must have at least 16 characters after
slugification, or the call is refused `[TKMN1]`; tokens already
issued are unchanged. From the same release, the tokens Pryv
generates (access, personal and password-reset tokens; 24
characters, as before) are drawn from the system's secure random
source, never from a non-cryptographic fallback `[SCTK2]`,
`[SCTK3]`. See A.8.5.

## ISO 27001 A.8.6: A.8.6 Capacity management

Coverage: facilitated · effort saved: medium · mode: infrastructure · draft

Requirement: The use of resources shall be monitored + adjusted in line with
current + expected capacity requirements.

**What Pryv does for you**

Pryv-side capacity
surfaces: per-core observability metrics (memory, CPU, latency,
request volume); horizontal scaling via adding cores to the
cluster (each handles its bound users + shared rqlite control
plane). Operator's capacity-planning cadence + provisioning
automation sit on top.

**Detail**

**Resource bounds inside the core (open-pryv.io 2.0.0-rc.47 and
2.0.0-rc.50).** One client can no longer exhaust a core's capacity
through a single call shape: a batch holds at most 1000 calls with
its results bounded together (`limits.batch.maxTotalItems`)
`[CEDB5]`, `[CEDB6]`; `events.get` paging is bounded and PostgreSQL
results are streamed through a cursor instead of loaded whole
`[EGLV1]`, `[EGLC1]`; uploads are limited in parts, files
(`uploads.maxFiles`) and size by default `[MPLM3]`, `[MPLD1]`;
socket.io namespaces exist only for user names and messages are
bounded (`socketIO.maxMessageBytes`) `[SION1]`, `[SION4]`;
previews refuse images declaring more than
`eventFiles.previewsMaxInputPixels` and render at most
`eventFiles.previewsRenderConcurrency` at once `[PVPX1]`,
`[PVRQ1]`; a crashing worker is replaced after a growing delay
`[WRBO1]`. These protect capacity; sizing the cores, watching the
metrics and scaling stay yours. See
`context/rate-limiting-and-dos-protection.md`.

**Password checks and database time (open-pryv.io
2.0.0-rc.87).** Password
hashing and verification, OAuth client secrets included, run at
most `auth.passwordCheckConcurrency` at a time per API worker
(default 2), with up to `auth.passwordCheckQueue` calls waiting
(default 50, at most 10 s); beyond that the call is refused
before anything is checked, so a flood of password checks no
longer takes the worker's CPU and thread pool from attachments,
webhook lookups and compression for every account `[CLIM1]`,
`[CLIM2]`, `[CLIM3]`, `[CLIB2]`, `[PCLM1]`, `[PCLM2]`. On
PostgreSQL, a statement issued while serving an API request is
stopped after `storages.engines.postgresql.statementTimeoutMs`
(default 30 s) and a transaction left idle is closed after
`idleInTransactionTimeoutMs` (default 60 s); the request answers
`503 api-unavailable` and one warning line is logged. A streamed
read is limited per batch of rows, so a long download is not cut.
Account deletion, background jobs, boot-time schema work,
`system.checkPlatformIntegrity` and the command-line tools run
unlimited on a small separate pool: each PostgreSQL pool of a
worker may open up to 2 more connections, so leave that headroom
in `max_connections` (tests `[PGSS1]`, `[PGSI1]`, `[PGSI2]`,
`[STMC1]`, `[MNSC1]`). Both apply to the workers of the clustered
server (`bin/master.js`). They bound how long one request holds a
connection and how much CPU password checks take; many slow
requests in a row are still for your edge layer to limit.

**Per-account, per-access and per-connection ceilings (the release
open-pryv.io 2.0.0-rc.90; on by default, per API worker, `0`
turns each off).** Authenticated calls running at once (HTTP, batch
counted once, socket.io) are capped per account
(`limits.requests.maxInflightPerUser`, default 64) and per access
(`limits.requests.maxInflightPerAccess`, default 32), so one shared
token cannot take its owner's whole budget; past either the call
answers `429 too-many-requests` with `Retry-After: 1` without running
`[APLM3]`, `[APLM5]`, `[APLM9]`. Calls without an access
(`auth.login`, password reset) are not counted. Parameters nested
deeper than `limits.json.maxDepth` (default 64) or with an object
holding more than `limits.json.maxObjectKeys` keys (default 10000)
answer `400 invalid-parameters-format` before the method runs
`[APLM1]`, `[APLM2]`. On socket.io: connections per access
(`socketIO.maxConnectionsPerAccess`, 20) and per account
(`socketIO.maxConnectionsPerUser`, 100), refused at the handshake
with `too-many-requests` `[SIOL1]`, `[SIOL3]`; calls running at once
on one connection (`socketIO.maxInflightCallsPerConnection`, 16)
`[SIOL5]`; scopes per connection (`socketIO.maxScopesPerConnection`,
100; refused with `invalid-operation`, the whole `subscribe` adds
nothing) `[SIOL6]`; a burst of access changes re-checks the open
connections at most once per second `[SIOL8]`. These are ceilings on
concurrent work, not request rates: per-token request rates stay at
your edge layer.

**Stream tree, stalled readers and mail (same release; on by
default, `0` turns each off).** A stream sits at most
`limits.streams.maxDepth` levels deep (default 32, a move counts the
moved subtree) and an account holds at most
`limits.streams.maxPerAccount` streams in its own store (default
10000, trashed ones included); past either the write answers `400
invalid-operation`, also when an access creates a stream from a
permission's `defaultName` `[STLM1]`, `[STLM2]`, `[STLM3]`,
`[STLM6]`. An event carries at most `limits.events.maxStreamIds`
distinct stream ids (default 100, `400 invalid-parameters-format`)
`[STLM4]`. An access holds at most `webhooks.maxPerAccess` webhooks
(default 10) and an account at most `webhooks.maxPerUser` (default
100), past either `webhooks.create` answers `400
invalid-operation`; a webhook carries at most `webhooks.maxScopes`
scopes (default 20, `400 invalid-parameters-format` on create and
update), so the outbound calls one account can make the core send
are bounded `[WHLM1]`, `[WHLM2]`, `[WHLM3]`. What an account already
holds stays readable, and webhooks already stored keep working. An HTTP
connection with no traffic either way for
`http.responseIdleTimeoutMs` (default 120 s) is closed, so a client
that stopped reading no longer holds a database cursor and call
slots `[RIDL1]`; keep it above your slowest call (websockets are
not affected). One access runs one streamed audit read at a time
per worker (`limits.audit.maxConcurrentReadsPerAccess`, default 1);
a further read waits for a slot, oldest first, up to
`limits.audit.maxReadWaitMs` (default 30 s), so parallel reads run
one after the other and succeed, and only a read left without a
slot past the wait answers `429 too-many-requests` `[RIDL3]`,
`[RIDL4]`, `[RIDL5]`. The mail
a caller can make a core send is capped per hour and per class
(`services.email.maxPerHour`, default 500, registration mails apart
from account mails) `[MLBG3]`; the per-address and per-account
mail budgets are on A.8.21.

**Routing lookups on a multi-core platform (same release; on by
default, `0` turns each off).** Which core hosts a username used to
be read from the platform database, at its most expensive
consistency level, for every `/{username}/*` request (the `421
wrong-core` check) and every embedded-DNS answer for
`<username>.<domain>`: a stream of requests or forged DNS queries
for random names became a stream of cluster-wide reads. Each process
now keeps the answer, a found mapping for
`cluster.userCoreCache.positiveTtlMs` (default 30 s) and an unknown
name for `cluster.userCoreCache.negativeTtlMs` (default 5 s);
concurrent misses for one name share one read, a failed read caches
nothing, and a name longer than any username is never cached
`[PUCC1]`, `[PUCC2]`, `[PUCC4]`, `[PUCC6]`, `[PUCC7]`. Uniqueness
checks (registration, renames) never use the cache. What it costs
you: an account moved to another core can be routed to its former
core for up to 30 s, and a name just registered can be unknown for
up to 5 s, on another core and on another process of the same core.
A client whose lookups found no account more than
`limits.routing.unknownNamesPerClientPerMinute` times in a minute
(default 60, per API worker) gets 429 for names not already cached
until the minute ends, so distinct random names no longer each cost
a read without bound `[CUCB2]`.
The embedded DNS also limits, per client network, the UDP answers
that need a lookup (see A.8.21) `[DRRL5]`; the read level is on
A.8.14.

## ISO 27001 A.8.14: A.8.14 Redundancy of information processing facilities

Coverage: facilitated · effort saved: high · mode: infrastructure · draft

Requirement: Information processing facilities shall be implemented with
redundancy sufficient to meet availability requirements.

**What Pryv does for you**

Multi-core Raft replication
makes the platform DB (user-to-core index, shared settings,
certificates) redundant, so the cluster keeps routing and serving
TLS when a peer fails. User data is not replicated between
cores: the users homed on a failed core are unavailable until
that core, or its restore from backup, is back. Redundancy of
user data is yours to add under the storage engine (e.g.
PostgreSQL streaming replication, replicated volumes). The
availability target + redundancy depth is operator policy.

**Detail**

Since open-pryv.io 2.0.0-rc.34 the replicated platform DB runs on
rqlite 10.5.1: a node killed while taking a snapshot no longer
risks restoring stale pages into its copy (as under 9.x),
snapshot files are checksummed, a node stops on a node-local
SQLite error instead of diverging, and the first write a follower
forwards to a restarted leader no longer fails once. Upgrading a
cluster is one-way for each node's data directory and needs the
nodes upgraded back to back (followers first, never adding a node
while versions are mixed): `open-pryv.io/INSTALL.md`, "Upgrading
the bundled rqlite (9.x to 10.x)".

**Routing reads (open-pryv.io 2.0.0-rc.90).** The
cached read of which core hosts a name (see A.8.6) asks rqlite for
the `linearizable` level instead of `strong`: just as up to date,
without a Raft log entry per read; the other reads of that mapping
stay `strong` `[RQRC5]`. Like before, it fails while the cluster has
no leader (rqlite waits up to 1 s by default). A `strong` or
`linearizable` read that rqlite answers with no result (no leader
yet) is now an error instead of "no such row", so during an
election a taken name no longer reads as free, nor a known one as
unknown `[RQRC6]`, and a failed read is not cached `[PUCC6]`. With
`storages.engines.rqlite.external`, the rqlited you run must support
the `linearizable` read level (the bundled one is 10.6.0, and
10.7.5 from open-pryv.io 2.0.0-rc.90). From that
release a platform write that rqlite answers without a result
(leader unreachable) is an error, where it was silently lost
`[RQNA1]`.

**Reads without an answer (the release after open-pryv.io
2.0.0-rc.89).** During a leader change, or when a core cannot
reach its local rqlited, a platform read that gets no answer is
sent again every 100 ms for up to
`storages.engines.rqlite.readWaitMs` (default 3000 ms, `0` = one
attempt) `[RQNR3]`, `[RQNR4]`, `[RQNR7]`. Still unanswered, the
call fails instead of acting on an absent row (a valid invitation
or OAuth code read as invalid, a name just reserved read as taken,
a held certificate as missing, a core as unknown) `[RQNR1]`,
`[RQNR5]`: the API methods, the routing of `/{username}/*`
requests, the `/reg/*` routes and the adapter ingress answer `503
api-unavailable` with `Retry-After: 2` `[PNAH1]`, `[PNAH2]`,
`[IGNA1]`, the OAuth endpoints `503 temporarily_unavailable`
`[ORNA1]`, and the embedded DNS `SERVFAIL` with no SOA, keeping the
records it holds `[DNNA1]`, `[DNNA2]`, `[DNNA3]`. An unanswered
platform write answers the same 503 (was 500). After one read
waited in vain, the next fail at once until one is answered, so a
long outage does not hold every request for the full wait
`[RQNR4]`. What stays yours: retry on 503 with `Retry-After` in
your clients and load balancer, and size `readWaitMs` to your
measured election time.

## ISO 27001 A.8.17: A.8.17 Clock synchronization

Coverage: facilitated · effort saved: low · mode: awareness · draft

Requirement: Clocks of information processing systems used by the organization
shall be synchronized to approved time sources.

**What Pryv does for you**

Clock sync stays your host's job (chronyd / ntpd): Pryv stores
whatever timestamp the host produces. Pryv makes a badly skewed
clock visible at the two points where it breaks a core: a new
core whose clock differs from the cluster's is refused at join,
and a TLS certificate outside the local clock's validity window
is neither installed nor hot-swapped.

**Detail**

Pryv's architecture is **core-affine**, every user's data
operations resolve to one core (see
`context/core-affinity-architecture.md`). Cores never need to
agree on clock value or on cert validity with each other; the
dangerous failure modes are all intra-core (one core's own
clock vs its own loaded cert / its own audit-row timestamps).

**Pryv's existing contribution to skew detection**: every API
response carries `meta.serverTime` (Unix timestamp seconds;
`components/api-server/src/methods/helpers/setCommonMeta.ts`).
Webhook payloads include the same. Clients use this to detect
their own clock skew vs the server.

**Shipped** (open-pryv.io `5266b697`, released after
2.0.0-rc.34; see
`proposals/clock-skew-cluster-checks.md`): two intra-core
checkpoints. (1) Bootstrap join: before acking, a new core
compares its clock with the issuing core's (`meta.serverTime`
of its API root, else the HTTP `Date` header) and refuses the
join beyond `--bootstrap-clock-skew-seconds` (default 30 s, `0`
disables); the join token is not used, so fixing the clock and
re-running succeeds. (2) Certificate load: a certificate whose
`notBefore..notAfter` window does not contain the local clock
(tolerance `cluster.clockSkewSeconds`, default 30 s) is not
materialized from PlatformDB nor hot-swapped into the workers,
and a custom certificate outside its window is reported at boot.
What stays yours: run a clock service on every host. Pryv does
no periodic clock polling.

- context notes: core-affinity-architecture

## ISO 27001 A.8.21: A.8.21 Security of network services

Coverage: facilitated · effort saved: medium · mode: infrastructure · draft

Requirement: Security mechanisms, service levels and service requirements of
network services shall be identified, implemented and monitored.

**What Pryv does for you**

Pryv's external
network surface is the TLS-terminating HTTPS API + the embedded
DNS server (when multi-core enabled); both are monitored via
observability. Inter-core mTLS is the internal surface. The

sits outside Pryv.

**Detail**

**General rate limiting / DoS protection stays operator-side**
(reverse proxy / WAF / API gateway): general in-process
throttling was rejected because (1) multi-core load distribution
makes per-core counters mis-fire and (2) abuse signatures are
operator-specific. Pryv contributes the **detection layer**
(audit log + observability metrics + `accesses.delete`
revocation) and, since open-pryv.io 2.0.0-rc.47, **targeted
in-code budgets** on the paths it can count correctly: failed
passwords per account and per client address across all cores
(`auth.passwordAttempts`) `[CEPB1]`, `[CEPI1]`; credential
methods refused inside batches and over socket.io `[CEDB1]`;
live `/reg/access` requests per address
(`access.maxLiveRequestsPerIp`) `[RAI1]`, a request nobody opens
living `access.unopenedRequestTtl` (600 s) `[RAU1]`; from the
release 2.0.0-rc.90, with `access.openedOnlyByAuthPage`
(default `false`) only the auth page's read (`?authPage=1`) opens
a request, so an app polling at once no longer keeps every
request alive for the hour `[RAU3]`, `[RAU4]`; turn it on once
your auth page sends the flag (a courtesy flag anyone can add,
the per-address budget unchanged); batch, paging, upload
and socket.io message bounds `[CEDB5]`, `[EGLV1]`, `[MPLM3]`,
`[SION4]`; and in 2.0.0-rc.50 an invitation-check budget
`[IVCK1]`, a `webhooks.test` interval `[WHTT1]` and preview
limits `[PVPX1]`. Failed MFA second factors have had a
per-account backoff since 2.0.0-rc.27
(`services.mfa.attempts.backoff`), see A.8.5. The per-address
budgets read the client address through `http.trustedProxies`
only: behind your reverse proxy, list it there `[CEPI2]`. The
embedded DNS server validates requests and bounds its TCP
connections (`dns.tcpMaxConnections`, 2.0.0-rc.46) `[DNR01]`.
From 2.0.0-rc.90 it also limits the UDP answers
that need a platform lookup (`<core>.<domain>`,
`<username>.<domain>`, found or not) to
`dns.responseRateLimit.perSecond` a second per client network
(default 20, per /24 IPv4 or /56 IPv6, all names counted together);
past it the answers are dropped except every
`dns.responseRateLimit.slip`-th (default 2), sent truncated so a
real resolver retries over TCP, which a forged source address
cannot. A refused query costs no lookup and is logged `[DRRL1]`,
`[DRRL2]`, `[DRRL5]`; other names (apex, static, service, hosted
sites) and TCP are not limited by it `[DRRL6]`. A public resolver
sending many clients' queries from one network meets the limit
first: past it, it retries, over TCP for the truncated answers, so
size this limit and `dns.tcpMaxConnections` for your traffic.
Forged queries for random names spread over many networks pass
that per-network limit: the same release also bounds, for the
whole DNS server, the UDP lookups of names it does not already
know that found nothing (`dns.responseRateLimit.missesPerSecond`,
default 100, lookups still running included, for at most 5 s);
past it such queries are refused the same way without a lookup,
while known names and TCP are still answered `[DRRL7]`, `[DRRL8]`,
`[DRRL9]`. During such a flood an existing account not resolved
in the last 30 s counts as unknown too and its resolver retries
over TCP. Core information (core names, an account's core, service
names, hosted sites) is answered from the core list the DNS
re-reads every 30 s, without a platform read per query `[DCIC1]`.
Routing lookups are cached per process (see A.8.6).
Since open-pryv.io 2.0.0-rc.87, password checks run a bounded
number at a time per API worker
(`auth.passwordCheckConcurrency`, `auth.passwordCheckQueue`):
past it the API answers `429 too-many-requests` and the OAuth
endpoints `503 temporarily_unavailable`, both with
`Retry-After`, and the refusal is never a failed attempt
`[CLIM2]`, `[PCLM1]`, `[PCLM2]`; on PostgreSQL the database work
of an API request is time-limited (see A.8.6). From the release
2.0.0-rc.90, each API worker also caps the calls running at
once per account and per access (`limits.requests.*`, `429
too-many-requests`), the nesting and size of call parameters
(`limits.json.*`, `400`), and socket.io connections per access and
per account, calls per connection and scopes per connection
(`socketIO.max*`) `[APLM1]`, `[APLM3]`, `[APLM9]`, `[SIOL1]`,
`[SIOL3]`, `[SIOL5]` (see A.8.6). They bound concurrent work, not
request rates. The same release closes an HTTP connection idle
either way for `http.responseIdleTimeoutMs` (default 120 s), so a
stalled reader no longer holds its call's resources `[RIDL1]`, and
bounds the mail a caller can make a core send: registration codes
per client address
(`account.emailVerification.registrationCodesPerIpPerHour`, 10 an
hour, `429 too-many-attempts`) `[MLBG1]`, verification mails per
account to distinct addresses
(`account.emailVerification.addressesPerAccountPerDay`, 10 a day)
`[MLBG2]`, and an hourly breaker per core counted apart for
registration and account mails (`services.email.maxPerHour`, 500),
so a flood of registration codes cannot stop password resets
`[MLBG3]`. Notices the platform sends on its own are not counted.
These budgets do not replace an edge layer for volumetric
traffic, per-token request rates and WAF rules. Full rationale +
operator mitigation patterns:
`context/rate-limiting-and-dos-protection.md`. Reference nginx +
fail2ban configuration, verified against a running core (per-IP
and per-token limits on the routes that matter, ban jails, limits
per workload profile, a load test proving the limits fire):
`customer-resources/rate-limiting.md` on the developer site.

## ISO 27001 A.8.26: A.8.26 Application security requirements

Coverage: facilitated · effort saved: medium · mode: awareness · draft

Requirement: Information security requirements shall be identified, specified
and approved when developing or acquiring applications.

**What Pryv does for you**

For the operator running
Pryv as one of its applications, this compliance matrix IS the
catalogue of identified + specified + approved security
requirements Pryv satisfies. For the operator's own applications
built on Pryv, the requirements are their editorial work.

**Detail**

Example of a requirement Pryv implements for you: content a user
uploads cannot attack other users through the API origin. Since
open-pryv.io 2.0.0-rc.34 an attachment whose declared type a
browser executes or renders as a document (HTML, SVG and other
XML, JavaScript) is served with `Content-Security-Policy:
sandbox; default-src 'none'` next to `Content-Disposition:
attachment`, on the token and the `readToken` paths alike
(`open-pryv.io/components/api-server/src/middleware/attachment-access.ts`).
Uploads are not refused for their type. If your app displays HTML
or SVG attachments, fetch the content and render it in your app's
own sandbox: that part of the requirement is yours.

A second example, in the sign-in flow: an authorisation request
(`POST /reg/access`) no longer has a `REDIRECTED` outcome
(open-pryv.io 2.0.0-rc.36, `62ab4f7e`, merged in
`1aa22e1a`). That status let anyone holding a request key store an
unvalidated URL that was then served to the authentication page
under a field such pages follow. It is now refused (`400
invalid-parameters`), no outcome post stores a `redirectUrl`, and
the poll never answers `REDIRECTED` `[MC04D]`. No shipped
authentication page sent it; if your own page did, it must stop
(a request stays on the core that created it, and an account on
another core is served through the shared-secret hand-off
between cores).

The address an authorisation request returns to (`returnURL`,
followed by the authentication page once the user answers) is
checked when the request is created, since the release after
open-pryv.io 2.0.0-rc.89: a value that is not absent or an absolute
URL, carries `user:password@`, or uses a `javascript:`, `data:`,
`vbscript:` or `blob:` scheme is refused (`400 invalid-parameters`)
`[RAO8]`, `[RTO10]`. With `access.returnOrigins` set, an app id
you list may only return to the origins you register for it
`[RAO3]`, `[RTO12]`. This is redirect hygiene, not client
authentication: whoever creates a request can still read its
outcome by polling; apps that need their redirect bound to the
client use the OAuth2 flow.

Mail sent through Mandrill: since the release after open-pryv.io
2.0.0-rc.89, `services.email.mergeLanguage: handlebars` makes
Mandrill HTML-escape the variables of `{{VAR}}` templates (names,
links, an administrator's reason) `[RSLK7]`. Unset, Mandrill uses
its account default, whose escaping it does not document, and the
core warns at boot `[CKML1]`. Converting the Mandrill templates and
setting the key are yours; the bundled in-process templates escape
by themselves.

Further examples from the 2026 security review (open-pryv.io
2.0.0-rc.49 and 2.0.0-rc.50; `context/code-security-review-2026.md`):
every JSON answer of the API carries `Cache-Control: no-store` and
`Vary: Origin`, so neither a browser nor a shared cache keeps API
answers `[HTC1]`; a hosted proxy site refuses a path holding an
encoded separator or a dot segment before it reaches the upstream
`[HSPE1]`; query strings are parsed without letting a key shadow a
built-in object property `[QPR2]`. If you put a cache or CDN in front
of the API, keep it honouring these directives.

Another, for outbound calls (open-pryv.io 2.0.0-rc.56): a URL a
counterparty supplies cannot make the server call an address it
should not reach. The cross-account, delegation and OAuth
revocation calls refuse, before any connection, a host that is or
resolves to a loopback, private, link-local or otherwise reserved
address (unless listed in `cmc.allowedPrivateHosts`), plain
`http:` and URLs carrying credentials, do not follow redirects and
stop reading an answer past 1 MiB `[PFR1]`, `[PFR2]`, `[PFR4]`,
`[PFR5]`, `[PFR6]`, `[CO22]`; a refusal names the host, never the
path or a token `[PFR10]`, and a refused delivery is not retried
`[CO21]`, `[RQ33]`. Since open-pryv.io 2.0.0-rc.70 a client's
`jwks_uri` key set, and since 2.0.0-rc.74 a client metadata
document and its key set, are fetched through the same guard, https
only whatever `cluster.allowInsecurePeerUrl` says, with the checked
address pinned to the connection, bounded size (64 KiB for a key
set, `oauth.clientMetadataDocuments.maxDocumentBytes`, default
16 KiB, for a document), a 5 s timeout and a budget of 10 document
fetches a minute per host; a document URL naming a host of your
platform is refused before any fetch `[OCMD01]`, `[OCMD03B]`,
`[OCMD03D]`, `[OCMD03G]`, `[OCMD03H]`, `[OCMDE17]`. Hosts listed in
`cmc.allowedPrivateHosts` are allowed for these fetches too, so
list there only peers you would let any client name.

**Adapter routes (open-pryv.io 2.0.0-rc.73, off unless
`adapterRoutes` is set).** The core forwards `/adapter/<name>/…`
(and optional `/.well-known/<label>/adapter/<name>/…` prefixes) to a
sidecar you run, before any API middleware: it authenticates
nothing on these paths and adds no CORS, audit or rate limit, so the
sidecar must authenticate every request and its port must not be
reachable from outside the host. What the core does enforce: the
upstream cannot be the platform or the core's own listener, an
encoded separator, dot segment or `%00` in the path is refused
before forwarding, bodies are capped (`maxBodyBytes`, default
1 MiB), idle requests time out (`idleTimeoutMs`, default 60 s),
`X-Forwarded-For` is set by the core and `X-Forwarded-Host` /
`-Proto` are taken only from a trusted proxy, and an https upstream
is verified against its own name `[ADRI03]`, `[ADRI06]`,
`[ADRI09]`, `[ADRI13]`, `[ADRC03]`, `[ADRC08]`. Since rc.75, on an
account host (`<name>.<dns.domain>`) the core tells the sidecar
which account the request addresses in `X-Adapter-Name` /
`X-Adapter-Base`, always removing client-sent copies (from a
trusted proxy too), and answers `421 wrong-core` without contacting
the sidecar when another core serves the account `[ADRU3]`,
`[ADRU4]`. These two headers are an address, not an identity:
upgrade each core before its sidecar relies on them, and do not let
an ingress route adapter paths around the core.

## ISO 27001 A.5.21: A.5.21 Managing information security in the ICT supply chain

Coverage: facilitated · effort saved: medium · mode: evidence · draft

Requirement: Processes and procedures shall be defined and implemented to
manage the information-security risks associated with the ICT

**What Pryv does for you**

Supply-chain risk at the Pryv layer is now actively managed
and CI-enforced (open-pryv.io master merge `9e2ee7ff`):
`scripts/audit-prod-deps` fails every build on high or
critical advisories affecting the shipped (`--omit=dev`)
npm tree, with accepted advisories documented in a
justified allowlist rather than silenced; a CycloneDX SBOM
of the source tree is emitted on every CI run and scanned
with Grype (build fails on critical findings); the Docker
base image is digest-pinned and the rqlite download is
checksum-verified before unpacking; on release tags the
published image additionally carries its own CycloneDX
SBOM, a keyless (OIDC) cosign signature, and a SLSA
build-provenance attestation that pullers can verify.

--ignore-scripts` in CI, and GitHub Dependabot alerts
continue underneath. Honest bound: the pinned base image
still carries OS-level CVEs that scanners surface (a
slimmer-base migration is tracked as a follow-up), so the
claim is detection, gating and attestation, not a CVE-free
image. The operator's broader ICT supply-chain programme
(vendor assessment, SLA reviews, contract clauses) sits on
top.

**Evidence**

- derives from: iso-27001.A.5.19, iso-27001.A.8.30
